## 为什么需要流程

AI 可以很快写出代码，但如果没有约束，很容易出现“功能越加越多、结构越来越乱、改一处坏三处”的情况。我的做法是把开发拆成三步：先写文档，再搭骨架，最后逐个功能收口。

## 第一步：把需求写成 PRD

PRD 不需要很长，但必须回答几个问题：

- 这个产品解决什么问题？
- 目标用户是谁？
- 哪些功能是必须的，哪些可以以后再做？
- 数据存在哪里？
- 怎么判断做完了？

例如个人作品集项目，MVP 只保留：个人信息、技能、项目、博客、联系表单，以及一个能修改这些内容的后台。评论、搜索、多用户都不在首期范围。

## 第二步：让 AI 生成骨架

骨架阶段只要求“能跑”：

1. 初始化 Vite + React + TypeScript。
2. 配置 Tailwind 和路由。
3. 建好前台与后台的目录。
4. 首页能显示占位内容。

这个阶段不追求样式细节，也不急着接后端。先让项目能启动，后面每加一个功能都能立即验证。

## 第三步：逐个功能实现与回归

每完成一个功能，就做一次完整检查：

- 页面是否能打开？
- 控制台有没有报错？
- 移动端是否溢出？
- 数据保存后刷新是否还在？

我通常会给 AI 一个明确的验收清单，而不是只说“继续优化”：

```text
请检查后台保存流程：
1. 未登录访问 /admin 是否跳转登录页
2. 错误密码是否提示
3. 修改姓名后保存，刷新首页是否生效
4. 保存失败是否保留表单内容
```

## 提示词的小技巧

好的提示词通常包含三部分：

1. **角色**：你是一名熟悉 React 与 Serverless 的前端工程师。
2. **上下文**：项目使用 Vite、Tailwind、Vercel Functions，数据存储在 GitHub 私有仓库。
3. **验收标准**：构建通过、无控制台报错、375px 无横向滚动。

比起“帮我做一个个人网站”，这样的描述能让 AI 少走很多弯路。

## 总结

AI 不是替代思考，而是放大思考。文档越清楚，AI 的输出越稳定；验收越具体，返工越少。把流程固定下来之后，开发一个完整的小项目会轻松很多。
